# GCP VM-Series NGFW Preflight

Issue: GitHub #613, "Implement GCP VM-Series / NGFW support".

This note records architecture guardrails for the upcoming implementation. It
is intentionally not an implementation plan. The issue is requirement-free, so
the GitHub issue title, body, and acceptance criteria are the product contract.

## Decision Boundary

GCP VM-Series support is not a new NGFW product type, a new range model, or a
separate lifecycle workflow. It must extend the existing provider-neutral NGFW
and range contracts:

- CMS owns user intent, ownership checks, credential hydration, and audit.
- Engine owns request lifecycle, status gates, and task dispatch.
- The provisioner owns provider-specific VM-Series creation, PAN-OS
  configuration, runtime operations, range attachment, and persisted state.
- GCP/GDC substrate details live behind provider metadata, validated runtime
  env/config loaders, Terraform/Helm/bootstrap contracts, and the existing
  cloud adapter seams.

No new ADR is required for this preflight because existing ADRs already cover
the relevant decisions: ADR-005 provider seams, ADR-006 Kubernetes security,
ADR-007 GCP Helm/bootstrap ownership, ADR-008 GCP fail-closed/network/secret
posture, ADR-009 shared auth seam, ADR-010 argv-array process execution,
ADR-011 backend bundle/runtime env ownership, ADR-017 range egress policy, and
ADR-022 documentation coverage. If the implementation intentionally changes any
of those postures, update the ADR registry and exception docs in the same
change.

## Cross-Cutting Layers

The intended design crosses these security and validation layers:

- Auth and ownership: Mission Control must enter through `cms.services`, which
  validates the acting user, NGFW ownership, one-active-NGFW semantics, and
  name-confirmed destructive actions. Do not let views, JS, or GCP-specific
  code query Engine rows directly to authorize NGFW operations.
- Credential-at-rest handling: authcodes, SCM PINs, and OTP values stay in CMS
  encrypted fields and hydrated specs. VM-Series SSH keys, GDC kubeconfig
  access, image credentials, bootstrap XML templates, and runtime DB/cache
  secrets stay as provider secret references. No plaintext `*-secrets.env`,
  ConfigMap, event payload, or persisted state field may carry secret values.
- Schema and shape validation: extend the existing shared schemas and
  provider-neutral state builders only when the public contract truly changes.
  Runtime GDC/VM-Series inputs must be validated by `config.load_gdc_*` and
  the generated-runtime inventory, not by ad hoc parsers in provision logic.
- Runtime env binding: GCP runtime values are generated by
  `scripts/gcp/render_runtime_env.py`, inventoried in
  `shifter/installation/runtime_inventory.py`, surfaced through the Helm
  runtime ConfigMap, and forwarded by `_GCP_PROVISIONER_ENV_KEYS`. VM-Series
  image, bootstrap, storage, data-network, and route-next-hop keys must use
  that path if they become deploy-time contract values.
- OS/process exposure: task and runtime operations must keep argv arrays.
  Kubeconfig and SSH private keys may exist only in short-lived temp files with
  restrictive permissions, never in shell strings or logged command bodies.
  `NGFWExecutor` is the PAN-OS SSH executor to extend; do not expand the older
  generic SSH executor for secret-bearing PAN-OS flows.
- Network policy: GCP platform/range VPC reachability remains owned by
  Terraform, ADR-008, and the GCP VPC firewall preflight. GDC VM-Series
  management and data networks must not be enabled by broad public SSH/RDP,
  broad NetworkPolicy exceptions, or unvalidated firewall loosening.
- Persistence and lifecycle: GCP NGFW state must persist explicit
  `cloud_provider: "gcp"`, `attachment_mode`, `route_next_hop_ip`,
  `data_attachment_id`, management IP, SSH secret ref, and
  `provider_metadata.gcp`. This avoids AWS fallback inference and lets range
  attach/detach, terminal access, start/stop, and teardown use one contract.
- Events and error envelopes: lifecycle notifications stay lightweight
  status events. Full provider state, secret refs, kubeconfig material,
  bootstrap object contents, command output, or PAN-OS transcripts do not
  belong in CMS events, Channels messages, API error bodies, or user-facing
  exceptions.
- Observability: log request IDs, statuses, attachment mode, counts, and
  fingerprints. Treat Secret Manager paths, bootstrap GCS object URLs, host IPs
  where avoidable, serials, and command output as sensitive or fingerprinted
  evidence rather than clear-text operational chatter.

## Extensibility Seam

The durable seam is `NGFWAttachmentConfig` plus
`attachment_mode`/`provider_metadata`. The obvious future variations are a
different GDC network attachment mechanism, a different VM-Series image import
path, alternate bootstrap XML/licensing inputs, or a later non-GDC substrate.
Those variations should be represented as parameters in the GDC VM-Series
config and provider metadata, not as new CMS app types, new range schemas, or
provider-specific branches in Mission Control.

For GDC VM-Series specifically, image URL, image credential secret,
bootstrap bucket, bootstrap XML template secret, namespace prefix, storage
class, management/data network names, static IP CIDRs, route-next-hop IP, and
sizing are the parameter boundary. Keep them backend-owned and validated.

## Gotchas And Anti-Patterns

- Do not conflate persistent Palo Alto VM-Series with AWS Network Firewall,
  GCP VPC firewall policy, Kubernetes NetworkPolicy, portal VPC inspection, or
  the `mcp/ngfw` read-only tool surface. They are different control planes.
- Do not implement a Compute Engine-only path under the GCP label while the
  accepted parity direction is GDC VM Runtime / KubeVirt.
- Do not create duplicate NGFW DTOs, status enums, exception hierarchies,
  schema validators, event types, or route attachment workflows.
- Do not make AWS compatibility fields such as `ec2_instance_id`,
  `data_eni_id`, or `gwlb_endpoint_id` required for GCP. Persist explicit GCP
  provider identity instead of relying on inference.
- Do not bypass CMS credential hydration/encryption or accept authcodes/PINs
  directly in GCP-specific views, APIs, Terraform variables, or env files.
- Do not log bootstrap ISO contents, authcodes, PINs, OTPs, kubeconfig data,
  raw Secret Manager paths, full provisioner outputs, or full persisted state.
  Existing logs around bootstrap GCS URLs and management/next-hop IPs should be
  tightened rather than copied.
- Range destroy currently treats NGFW cleanup as best effort. If GCP detach
  fails, state consistency must still be observable and recoverable; otherwise
  later NGFW teardown can incorrectly believe a range is still attached or no
  longer attached.
- GCP range pause/resume support is currently incomplete in the range runtime
  path. Acceptance criteria for operational validation must either close that
  parity gap or state a narrower behavior contract explicitly.
- GCP NGFW range provisioning currently requires the NGFW to already be ready;
  AWS can auto-resume a paused NGFW. Treat that as a parity gap, not as an
  implicit product decision.
- VM-Series host-key behavior matters because `NGFWExecutor` uses strict host
  key checking. Any first-boot trust path must be explicit and test-covered.
- `pycdlib`, `kubectl`, the virt plugin, GCP client libraries, image-import
  credentials, GDC access secret shape, and bootstrap bucket permissions are
  runtime prerequisites. They belong in deployment/bootstrap validation and
  docs, not in silent provisioner fallbacks.
- GCP state that includes `data_attachment_id` must also include
  `cloud_provider: "gcp"`; otherwise provider inference can misclassify it as
  AWS.
- Major user-visible NGFW/platform changes must keep ADR-022 documentation
  coverage current. The existing NGFW user and technical docs are the first
  place to update.

## Non-Goals

- This preflight does not implement #613.
- Do not add a formal Ground Control requirement for this run.
- Do not introduce a new public NGFW product/app type, new authentication
  framework, new event bus, new secret store abstraction, or new task runner.
- Do not redesign portal inspection, AWS Network Firewall, AWS VM-Series
  behavior, or the range isolation model except where compatibility tests
  require preserving current behavior.
- Do not weaken ADR-008 GCP fail-closed posture, Kubernetes Pod Security,
  NetworkPolicies, Cloud Armor, private operator access, runtime secret
  handling, or Terraform/Kubernetes validation to make VM-Series provisioning
  easier.
- Do not replace root/backend-bundle ownership of GCP Terraform, Helm,
  runtime env, bootstrap, and health checks with deployment-local scripts.
- Do not treat the bootstrap object, kubeconfig, or VM-Series licensing inputs
  as durable user-facing data; they are operational artifacts and secrets.

## Validation Surface

Implementation touching architecture, workflows, hooks, or
`shifter/shifter_platform` must pass:

- `python3 scripts/adr_guard/adr_guard.py --all --level ci`
- `cd shifter/shifter_platform && uv run lint-imports --config ../../.importlinter`

Additional checks depend on the touched surface:

- Provisioner Python: targeted provisioner pytest around GDC VM-Series
  lifecycle, NGFW attachment state, range attach/detach, start/stop, and
  provider inference.
- GCP runtime renderer: `scripts/gcp/tests/test_render_runtime_env.py` and
  runtime inventory checks.
- Terraform: `TFLINT_CONFIG="$(pwd)/.tflint.hcl"; cd platform/terraform && tflint --recursive --config "$TFLINT_CONFIG"`.
- Kubernetes/Helm manifests: `actionlint`, `kube-linter lint --config
  .kube-linter.yaml platform/k8s/`, and `kubeconform -strict -summary
  -ignore-missing-schemas -kubernetes-version 1.31.0
  platform/k8s/gcp/base/*.yaml`.
