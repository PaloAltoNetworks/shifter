Scoped the GCP application workload identities (portal, workers, CTF scheduler, provisioner) off broad project-level IAM: Secret Manager access is now bound per named runtime secret and Cloud Storage access per named bucket, driven by a single canonical workload/resource matrix in the `portal/iam` module (ADR-008-R7). A repo-native Terraform guard (`scripts/check_tf_gcp_iam_resource_scope`, wired into pre-commit and CI) fails closed on any project-level Secret Manager payload/admin or Cloud Storage object-admin grant to a workload identity, and effective-permission tests assert each identity's required resource set. Two dynamic-secret grants that cannot yet be resource-scoped (portal guest-credential reads and the provisioner's per-range secret lifecycle) remain project-level as documented, expiring allowlist residuals; the dedicated range-secret project/broker boundary that removes them is tracked in #1586.
